Полная архитектура базы данных интернет-магазина

Данная база данных построена на PostgreSQL и реализует нормализованную реляционную структуру для:

хранения товаров;
хранения типов товаров;
хранения материалов;
хранения типов материалов;
хранения флагов и фильтров;
хранения стоимости изготовления;
обеспечения работы Telegram WebApp;
обеспечения работы API;
поддержки масштабирования.
Общая концепция базы

База разделена на логические сущности:

Сущность	Назначение
products	Товары и услуги
products_type	Типы товаров
flags	Фильтры/теги
flags_for_products	Связи товаров и флагов
materials_type	Категории материалов
materials	Конкретные материалы
materials_for_products	Стоимость и доступность материалов
Главная схема зависимостей
products_type
    │
    │ ONE TO MANY
    ▼
products
    │
    ├───────────────┐
    │               │
    │               │
    ▼               ▼
flags_for_products  materials_for_products
    │               │
    │               │
    ▼               ▼
flags          materials_type
                    │
                    │ ONE TO MANY
                    ▼
                materials
Основные принципы архитектуры
1. Нормализация данных

База построена по принципам:

1NF
2NF
3NF

Это означает:

нет дублирования;
нет массивов внутри строк;
каждая сущность хранится отдельно;
связи реализованы через FOREIGN KEY.
2. Масштабируемость

База легко расширяется:

Можно добавить:

заказы;
пользователей;
корзины;
платежи;
фотографии;
характеристики;
SEO;
мультиязычность;
складской учёт.

Без изменения текущей архитектуры.

3. Безопасность данных

Используются:

PRIMARY KEY
FOREIGN KEY
UNIQUE
CHECK
CASCADE
RESTRICT

Это предотвращает:

битые связи;
дубли;
отрицательные цены;
удаление используемых сущностей.
4. Производительность

Созданы индексы для:

поиска;
JOIN;
фильтрации;
API-запросов.

Назначение

Главная таблица всей системы.

Хранит:

физические продукты.
Структура
Поле	Тип	NULL	UNIQUE	Описание
id	INTEGER	NO	YES	ID товара
code	VARCHAR(100)	NO	YES	Код товара
name	VARCHAR(200)	NO	NO	Название
products_type_id	INTEGER	NO	NO	Тип товара
Поле code

Используется:

Telegram-ботом;
API;
WebApp;
скриптами;
импортом;
экспортом.
Почему code важнее id

ID:

1
2
3

может меняться.

А code:

MODEL_RED_001

остаётся постоянным.

UNIQUE(code)

Гарантирует:

невозможно создать два одинаковых кода
products_type_id

FOREIGN KEY:

products.products_type_id
→ products_type.id
ON DELETE RESTRICT

Нельзя удалить тип товара,
если товары ещё существуют.

Почему это важно

Без этого:

товары останутся без типа

что приведёт к повреждению структуры.

Индексы

Ускоряет:

WHERE code = 'MODEL001';
idx_products_type

Ускоряет:

SELECT * FROM products
WHERE products_type_id = 1;

ТАБЛИЦА: flags_for_products
Назначение

Реализует MANY TO MANY связь.

Связь
products ↔ flags
Почему нельзя хранить флаги в products

Плохой вариант:

"Новинка, Хит, Premium"

Проблемы:

нельзя индексировать;
плохой поиск;
плохая фильтрация;
невозможно JOIN.
Правильный вариант

Отдельная таблица связей.

Структура
Поле	Тип
products_id	INTEGER
flags_id	INTEGER
PRIMARY KEY(products_id, flags_id)

Запрещает дубли.

Пример

Допустимо:

1 | 1
1 | 2
1 | 3

Недопустимо:

1 | 1
1 | 1
ON DELETE CASCADE

Если удалить товар:

удаляются все связи с флагами
Почему CASCADE здесь правильный

Потому что:

связь не имеет смысла без товара
